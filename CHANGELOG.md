- **Selected progressive, `CategoryArchetype`-governed request intake and rejected the universal form as the primary model.** The question set is data derived from `CategoryAttributeDefinition`, so adding a `Category` adds no screen and requires no application-shell redesign. `docs/04-ux/request-intake.md` maps all twenty-four items of the David-supplied competitor capture to a Superola disposition — including the three Superola declines outright: automatic fan-out (`WA-02`); a required minimum and maximum budget, which `EligibilityDecision` does not consider and which would therefore block a submission on a field that changes no outcome; and in-composer provider suggestions, which are a result slot with no ranking explanation at the moment of highest intent and the first surface a sponsored inventory would colonise.
- **Closed the two decisions the technology track deliberately handed to product, and gave the third a disposition.** `ADR-020` web rendering → **recommend Option A**, server rendering plus progressive enhancement plus **three** named client islands against the ADR's own ceiling of five. `ADR-019` Level 3 → **no rendered map in V1**, deferred with three named triggers. AI-assisted request intake → **`FUTURE`, not V1**, worth testing only under four named conditions. **None of the three is approved, and each needs David's individual signature.**
- **The rendering finding, and why it is not framework preference:** no V1 surface requires client state that survives navigation. The strongest counter-case is the multi-step composer — and its state is already a domain aggregate. `RequestDraft` exists in `ADR-003` precisely so pre-delivery content is durable and reusable, and browser-local storage covers the anonymous window `WA-05` opens. Solving it with a client framework would duplicate an aggregate the domain owns, on the client, where `ADR-011` forbids validation from living. **The second-order observation is the honest one:** three architecture decisions taken for unrelated reasons — no realtime transport, no availability model, and now no rendered map — removed the three surfaces that usually force a rich client on a marketplace. **Option A wins partly on the absence of the surfaces that would beat it**, which also names exactly what would reopen it.
- **The map decision was taken on user value and explicitly NOT on privacy.** The precise-location invariant is retained absolutely, and P03.1 had already corrected the conflation of an invariant with a product conclusion — a city centroid or a declared coverage area emits nothing private. The reason is that no V1 journey needs one. The strongest candidate, Fixed venue, is answered by a coarse `Place` label, the published venue address where the provider chose to publish it, and a **link-out to the customer's own map application**, which is not a rendered map: no tiles, no SDK, no dynamic-map cost line, no attribution or storage clause. **And the decision is falsifiable** — `R-055` requires service-area or travel-distance to be an available decline reason, so comprehension failure appears in Phase-1 data rather than in anecdote.
- **Recommended guest-then-verify customer identity** (`WA-05`, `Q-018`): anonymous discovery, profile viewing and composition; account and contact-channel verification at submit, before delivery, with the request durably stored as `PendingVerification` so the customer's work is never lost. **The honest cost is stated rather than buried:** verification abandonment (`R-022`) concentrates at that step, and `R-051` requires it to be instrumented **separately** from composer abandonment, because a blended number cannot distinguish "the form was too long" from "the customer would not give an email" and the fixes are opposite.
